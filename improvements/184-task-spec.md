# 改善提案 (タスク 184 の失敗より)

- 分類: task-spec
- 確度: medium
- 要約: Summary完全記載と追記15行上限が矛盾し、レビュー指摘が3ループ往復した
- 診断: /home/ojin/projects/3dreviewer/logs/184/diagnosis.md

## 何が起きたか
- **verify は3ループとも合格。** `final-verify.log:2` に「結果: 合格」とある。shared 129件、server 287件、web 940件がすべて成功している(`final-verify.log:45,118,282`)。typecheck も通った。実装とテストは失敗の原因ではない。
- 失敗の理由は、最終レビューの P2 指摘1件だけ。`server/server_Summary.md` の追加行が `git diff --numstat` で20行あり、完了条件の「server は追記15行以内」を5行超えている(`final-review.md:3-6`)。20行という数値はレビュー役の報告で、私は numstat を直接確認できていない(未確認)。
- ループごとの経緯は次のとおり。Summary の内容が足りないという指摘と、行数が多すぎるという指摘が交互に出ている。
  - loop1 review: 公開インターフェイス欄が旧仕様のままで、DB API・resolveUserId/rotateSession・AppDeps 拡張が載っていないと指摘(`loop1-2-review.md:9-11`)。fix で追記した(`loop1-3-fix.md:4`)。
  - loop2 review: 追記が33行で、15行上限を超えていると指摘(`loop2-2-review.md:4-6`)。fix で「33行→15行へ圧縮」した(`loop2-3-fix.md:3`)。
  - loop3 review: 公開インターフェイス欄が不完全だと、loop1 と同じ指摘を「既出(loop1)」として再度出した(`loop3-2-review.md:3-6`)。fix で DB・セッション・AppDeps・マイグレーションの情報を追記した(`loop3-3-fix.md:3-7`)。
  - final review: 追記が20行で上限超過と指摘し、loop2 の指摘に戻った。
- Summary の総行数は 241 行(現ワークツリーを実測)。300 行の上限には十分余裕がある。

## 根本原因
1. **タスク md の完了条件同士が両立しにくい。** このタスクでは server 側に公開 API が一気に増える。findSession/deleteSession、accounts.ts の6関数、password.ts、recovery-code.ts、resolveUserId/rotateSession/ACCOUNT_SESSION_MAX_AGE_SECONDS、AppDeps の2項目、migrate の5列と UNIQUE INDEX、/api/account の3ルートである。一方で、Summary は公開インターフェイスをすべて反映する規範になっている。そこに「追記15行以内」の上限が付いており、両方を満たす余地がほとんどない。
2. **「追記」の数え方が決まっていない。** レビュー役は `git diff --numstat` の added を数えている。この数え方だと、既存行を書き換えただけでも追加行に入るので、実質の上限はさらに厳しくなる。
3. **fix 役が累積の差分を見ていない。** loop3 の fix 役はタスク md の15行制約を読んでいた(`loop3-3-fix.log:374`)。しかし行数の確認は `git diff -- server/server_Summary.md`、つまり直前のコミットとの差分だけで行っていた(`loop3-3-fix.log:996`)。完了条件が意味する main...HEAD の累積量は見ていない。そのため、loop2 で15行に圧縮した分に上乗せしたことに気づかなかった。
4. **orch 側でも往復を止められなかった。** loop3 のレビュー役は過去の指摘を把握していた(「既出(loop1)」と書いている)。それでも、loop2 で出た逆向きの制約(15行上限)と比べないまま、追記を求めた。orch のプロンプトや実装が過去ループの指摘をどう渡しているかは、`/home/ojin/projects/3dreviewer/src/` が存在せず読めなかったため未確認。

## 推奨する対応
1. **タスク 184 の完了条件を書き直す。** 例:「server_Summary.md を更新している(全体300行以内。公開インターフェイス欄は関数名の列挙で足り、シグネチャの詳細は不要)」。行数上限を残すなら、根拠(`git diff --numstat main...HEAD` の added)と、公開 API の数に見合う値(25〜30行程度)を明記する。
2. **現ワークツリーはそのまま使える。** 実装と verify は合格で、指摘は Summary の行数だけ。人間が `server/server_Summary.md` を確認し、条件を緩めたうえで 184 をマージするか、Summary だけ手で整えてからマージする。一からやり直す必要はない。
3. **後続の 185〜189 も確認する。** 同じ「追記 N 行以内」の書き方が入っていないか見る(182 は12行、183 は5行の実績がある)。API を大きく増やすタスクには上限を付けないようにする。

## オーケストレータ側の改善
### 理由
- **レビュー側の改善:** レビュー役のプロンプトに、過去ループで出た逆向きの指摘(行数上限など)を必ず渡す。新しい指摘がそれと衝突する場合は、FAIL を繰り返さずに「完了条件の矛盾」として報告させ、ループを打ち切るようにする。今回なら loop3 の時点で task-spec の問題として止まり、2ループ分を節約できた。
- **fix 側の改善:** fix フェーズの自己確認で、行数を `git diff main...HEAD` の累積で測るよう指示する。あるいは、完了条件にある数値の上限を orch が機械的に累積差分で検査する。これで loop3 で上乗せしたような見落としを防げる。
- **副作用:** 矛盾の検出を優先すると、本当は実装で両立できたケースまで task-spec 扱いで早めに止める可能性がある。その場合、人間の確認が増える。
- `src/` が見つからなかったため、現在のプロンプト構成は確認できていない。改修する箇所は特定できておらず、上の改善は方針としての提案にとどまる。
