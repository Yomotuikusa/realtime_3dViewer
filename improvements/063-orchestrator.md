## 何が起きたか
- **loop1 実装**(commit 0cd99d8): 実装役が reads 指定のみの `web/tests/review-stores.test.ts` に `fps: 24` の期待値を1行追加した。logs/063/loop1-1-implement.log:7153 で patch 対象に含まれている。verify は合格(logs/063/loop1-verify.log:2)。

- **loop2 実装**(commit 2999538): orch は実装役に「前回ループのレビュー(参考)」として **修正前の loop1 レビュー**をそのまま渡した(loop2-1-implement.log:726-739)。修正フェーズで解消済みという情報も、現在の機械検証結果も渡していない(「機械検証で検出された違反」ブロックは loop2 実装ログに存在しない)。実装役は `git diff HEAD^ HEAD` で修正コミットの差分(`-fps: 24` → `+なし`)を見て「owns 外変更が残っている」と逆に読み(loop2-1-implement.log:2689)、`fps: 24` を**再追加**する patch を当てた(:2690-2704)。
- **loop2 verify**: 合格(logs/063/loop2-verify.log:2、54 files / 351 tests)。
- **loop2 レビュー**: PASS、申し送りに同ファイルを再掲(logs/063/loop2-2-review.md:9-10)。
- **orch の停止判定**: owns 外に同じファイルが残っているため「ループを重ねても変わらない」と判断し、修正フェーズを起動せずに失敗確定した。実際には loop1 末尾で一度解消しており、loop2 で新規に再発した違反である。

現在のワークツリー(task/063 @ 2999538)で main と差分のある owns 外ファイルはこの1ファイルのみ(loop2-1-implement.log:2562-2590 の変更一覧 + 当該ファイル)。main は 4e5fd76 で task/063 の基点と同じなので、main の取り込みは不要。

## 根本原因
主因は orch のループ間の引き継ぎ設計にある。
1. **古いレビューをそのまま次ループの実装役へ渡す**: 修正フェーズを経た後なのに、修正前の指摘(owns 外変更あり)だけを「参考」として渡し、修正済みであることや現在の機械検証結果を渡さない。実装役はこの指摘を「未解決」と信じて行動した。
2. **停止ヒューリスティックが「持続」と「再発」を区別しない**: 前ループ末尾のコミットで違反が解消していたかを見ずに、同名ファイルが loop2 に再び現れただけで「修正役では解けない持続的違反」と判定し、修正フェーズを飛ばして停止した。修正役なら1行の revert で解ける状態だった。

副次要因:
- **実装役の差分の読み違い**(implementation): 修正コミットの差分方向を逆に解釈した。ただし引き金は上記 1 の誤誘導。
- **タスクmd の矛盾**(task-spec): 振る舞い表の最終行(tasks/063-web-timeline.md:573)は `resetReviewStores()` 後の `fps 24` を期待値として挙げつつ「テストは足さなくてよい」と注記し、一方で完了条件(:661)は「振る舞い表の全行に対応するテストがあり」と要求する。当該ファイルは reads のみ(:7)。loop1 実装役が owns 外へ手を出した動機はこの矛盾と推測する(ログに明示の理由記述は無く、未確認)。

orch 本体のソース(src/*.rs、README.md)はこのリポジトリに存在せず参照できなかったため、上記 1・2 の内部実装の詳細は未確認。ログに残ったプロンプト内容と停止メッセージから判断している。

## 推奨する対応

3. orch 側は下記の改修を検討する。

## オーケストレータ側の改善
### 理由
設定値ではこの失敗を防げない(max_loops は残っていたが、停止判定はループ上限ではなくヒューリスティックによる)。改修すべき点は2つ:

- **次ループの実装役への引き継ぎ内容**: 修正フェーズを経た場合は、修正前のレビュー原文ではなく、修正役の最終報告と「現在の機械検証結果」(owns 違反の有無と、あれば `git diff main...HEAD` の実差分)を渡す。修正フェーズのプロンプトには既に「【機械検証で検出された違反】」ブロックがあるので、同じ形式を実装フェーズにも付け、違反が無ければ「なし」と明記する。これで「解消済みの指摘を未解決と誤認して再発させる」経路が塞がる。
- **停止判定の根拠**: 「loop N で owns 違反が残っている」と判定する前に、前ループ末尾のコミットで同ファイルが main と一致していたかを確認する。一致していたなら再発であり、持続ではない。再発なら通常どおり修正フェーズを起動する(loop 上限内で)。持続と判定するのは、前ループの修正フェーズを経ても同ファイルが main と異なり続ける場合に限る。

副作用の見立て: 実装フェーズのプロンプトが少し長くなる程度。停止判定の変更は、真に持続する違反(BLOCKED 相当)に対する早期停止を損なわない。前ループ末尾で一致していなかった場合の挙動は現状と同じ。
